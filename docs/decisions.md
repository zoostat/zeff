# Decisions

This file records every engineering decision taken during the work, each with its date, the choice and the reason, so that the owner and any later session can see why things are as they are. Questions only the owner can answer are not settled here; they go to `docs/spec/zeff_open_decisions.md`.

## 18 October 2026: Rust toolchain

**Choice.** The toolchain is pinned to Rust 1.99.1 (stable) in `rust-toolchain.toml`, and the Rust edition is 2024.

**Reason.** 1.99.1 was the current stable release when the repository was created, and edition 2024 is the newest stable edition that compiler accepts. A pinned version makes every machine and the continuous-integration job build with the same compiler, which the determinism rules need. The Rust edition is a separate matter from the Zeff language edition, which the specification sets (section 2).

## 18 October 2026: Specification freeze

**Choice.** The specification freeze (open decision #40) is in force from the first commit of 0.1.0.

**Reason.** The documents in `docs/spec/` are the authority. From the first commit of 0.1.0 their normative text changes only to correct an error found while coding, and each such change is logged in `docs/spec_changes.md`. Any other design question becomes a new entry in `docs/spec/zeff_open_decisions.md` with a deadline release.

## 18 October 2026: Workspace layout and crate names

**Choice.** One Cargo workspace. Engine kernel crates in `kernel/` (`zeff-columns`, `zeff-numeric`, `zeff-registry`); packages in `packages/tier<N>/<name>` (so far `packages/tier0/core` and `packages/tier1/data`, crates `zeff-core` and `zeff-data`); the language and engine crates in `crates/` (`zeff-syntax`, `zeff-ir`, `zeff-engine`, and `zeff-cli`, whose program is called `zeff`); build tooling in `tools/xtask`. A package's `src/`, `help/`, `tests/` and `functions/` folders follow the "Files" layout of section 9.1 and are created when the first function needs them.

**Reason.** The folder says what a crate is, so the tier check reads rules from paths and cannot be fooled by a crate's name. Kernel modules are fixed by section 8.1, rule 8; I split them into three crates for 0.1.0 (column store, numeric routines, registries) and `zeff-kernels` (linear algebra) is not created before 0.4.0, which needs it. Parser, typed IR and interpreter are not kernel modules, so they sit in `crates/` and `core` never depends on them.

## 18 October 2026: The tier rule check

**Choice.** `cargo run -p xtask -- check-tiers` reads the workspace's dependency graph and fails when: a kernel crate depends on anything but kernel crates; `core` depends on anything but kernel crates (outside crates included, test-only dependencies excepted); a package depends on a higher tier, on a later package of its own tier, or on an engine crate. A package folder not named in section 8.2 is also refused. It runs in CI as the job `tiers` and its rules are tested on crafted dependency graphs.

**Reason.** Section 8.1, rules 1 to 3 and 8, ask for a build failure rather than a convention. Reading `cargo metadata` needs no parsing of manifests by hand.

## 18 October 2026: Build profile and lints

**Choice.** Edition 2024 for every crate; `unsafe_code` denied in the whole workspace (a kernel may allow it locally when explicit SIMD arrives in 0.4.0, with a note here); clippy's default lints denied; integer overflow checks on in every profile; release builds use `opt-level = 3`, one code-generation unit and full link-time optimisation. No flag enables fast-math or fused multiply-add, and Rust does neither unless written explicitly. The toolchain file now also installs `rustfmt`, `clippy` and the `wasm32-unknown-unknown` target.

**Reason.** Determinism (section 8.3, point 3) and the rule that an Int overflow is an error (Language Reference, section 3.7). A single code-generation unit makes release builds reproducible.

## 18 October 2026: Continuous integration for the four targets (plan for step 3)

**Choice.** On GitHub-hosted runners of this public repository: Linux x86-64 on `ubuntu-latest`; Linux ARM64 on `ubuntu-24.04-arm`; macOS ARM64 on `macos-latest`; WebAssembly (with SIMD128) built with `wasm-bindgen` and run under Node on `ubuntu-latest`. Each job prints one hash per conformance case, and a last job compares them and fails on any difference. The second x86-64 SIMD level (the one without AVX-512) is covered for now in two ways: the x86-64 job writes the runner's CPU flags to its log, and the same source is also built for a wider instruction level (`target-cpu=x86-64-v3`) and its hashes compared with the baseline build, which shows that a wider machine cannot change a result. A self-hosted runner of a different SIMD level can replace this later (risk R9). Step 3 may refine this and will record any change here.

**Reason.** Hosted runners are free for public repositories, and the kernels use fixed 128-bit SIMD with no run-time dispatch (section 8.3), so the bytes that matter are those of the baseline build.

## 18 October 2026: Numeric kernel, algorithms and contract

**Choice.** `zeff-numeric` holds `sum`, `mean`, `variance` and `sd` over slices of `f64` without missing values. `sum` is a Neumaier compensated sum, left to right; `mean` is that sum divided by the count, then corrected once by the mean of the deviations; `variance` is the corrected two-pass algorithm (sum of squared deviations less the square of the summed deviations over n), divided by n − 1, never negative; `sd` is its square root. An infinite or overflowing sum returns the plain IEEE sum (`Inf`, or not-a-number for `Inf` with `-Inf`); a variance with any non-finite value is not-a-number; the column layer turns both into the language's rules for infinity and `NA` (Language Reference, section 4.1). Fewer than one value (mean) or two (variance) gives `None`.

**Reason.** Section 13 asks for compensated sums and two-pass variances. A fixed left-to-right loop of `+`, `-`, `*`, `/` and `sqrt` has the same bits on every target; `sqrt` is correctly rounded by IEEE 754 and WebAssembly. The one correction pass on the mean costs little and brings the result to within a rounding of Python's exact value. Skipping `NA` and its warning belong to the column layer, so the kernel stays a pure function of the valid values.

## 18 October 2026: First reference tests (Python `statistics`)

**Choice.** `tests/reference/descriptive.py` writes `tests/reference/descriptive.json` from Python 3.14.8's `statistics` module (exact rational arithmetic, rounded once) for five datasets: a small hand-made one, 1,000 values near 1e9 with a spread below 1, 500 values over sixteen orders of magnitude, a constant one, and two values. The data come from a seeded generator, are stored as text that reads back to the identical double, and are parsed in Rust with `str::parse`, so no value changes on the way. The Rust test requires 1e-12 relative agreement, tighter than the closed-form class (1e-6). The script is re-run only by hand; the JSON is committed. Step 15 adds the CI job that runs the script and compares.

**Reason.** Testing handbook, section 1.1: Python's `statistics` is the reference for 0.1.0. Storing text avoids the one-unit-in-the-last-place error some JSON readers make when parsing numbers.

## 18 October 2026: The conformance report and the four-target identity check

**Choice.** A new crate `zeff-conformance` (in `crates/`) holds the conformance cases: the four reducers on nine datasets (three of 5,000 to 10,000 generated values, and edge cases: constant, pair, single, empty, infinite, mixed infinite) and four "canary" cases that would show a target fusing a multiply and an add, flushing subnormal numbers, or rounding a basic operation differently. Data come from SplitMix64 (integer arithmetic only), so every target generates the same numbers. Each case reduces to a 64-bit FNV-1a digest of the result's IEEE bit patterns (every not-a-number reduced to one pattern), printed as a `name digest` line, with a comment line giving the raw bits to show where two targets part. The expected report is committed (`crates/zeff-conformance/expected.txt`); a unit test checks the native build against it and a change to any result is a deliberate edit of that file. FNV is for spotting differences only; the published checksums of `zeff selftest` (0.3.0) will use BLAKE3 (section 8.7).

CI runs the report on: Linux x86-64 at the baseline instruction set; the same Linux x86-64 runner with a release build for `x86-64-v3` (the second SIMD level, as planned above); Linux ARM64 (`ubuntu-24.04-arm`); macOS ARM64; and WebAssembly with SIMD128 under Node (`wasm-bindgen` 0.2.129 command line tool, installed with cargo and cached, `--target nodejs`). A last job runs `cargo run -p xtask -- compare-identity reports 6`: the four native reports, the WebAssembly report and the committed one must agree line for line, and the job fails when a report is missing, extra, malformed or different. The comparison has its own unit tests, including a report with one changed digit.

**Reason.** Risk R2: the check runs from the first commit while the code is small. A committed expected report stops all targets drifting together unseen. Loading the WebAssembly engine through `wasm-bindgen`, as the browser will, makes the later bundle-size figure (step 4) the realistic one.

## 18 October 2026: Bundle size and cold start, thresholds and method

**Choice.** `tools/bundle/measure.cjs` (Node only, no dependency; Node has gzip and brotli built in) measures the files `wasm-bindgen` writes for the browser engine: raw, brotli (quality 11) and gzip (level 9) sizes of the `.wasm` and `.js` files, and the cold start, which is the median of five fresh Node processes, each timing the load (compile and instantiate) and the first call. It writes `bundle.json`, prints a table, adds the table to the job summary, and exits 1 over a limit. The limits: **5,000,000 bytes** of brotli-compressed bundle (the early warning of risk R4, "passes 5 MB before 0.7.0") and **1,000 ms** of cold start. The step runs in the WebAssembly job on every push, and `bundle.json` is kept as the artefact `bundle-wasm`. The script's logic is tested with `node --test` (5 tests), and a deliberately tight limit was shown to fail the run.

**Reason.** R4 asks for size and start time to be tracked from 0.1.0. The cold-start limit is half of Zemp Lite web's 2 s target, leaving the other half for the page and the interface; it is a decision of mine, to be revised when the browser path exists. Until `zeff-engine` is built for WebAssembly (step 13 onwards) the measured bundle is the conformance crate, which is a floor, not the engine; the step that wires the engine into the WebAssembly job switches the measure to it. No size optimisation (`opt-level` for size, `wasm-opt`) is applied yet; it is considered when the size passes half the limit.

## 18 October 2026: Diagnostics crate and data model

**Choice.** A new crate `crates/zeff-diagnostics`, with no dependency, below the parser: the parser, the typed IR and the engine all produce diagnostics, so none of them can own the type. A `Diagnostic` holds a code (`Z` or `W` and four digits, checked), a severity (error, warning, note), a message, the file name, labelled spans (one primary, any number of secondary), help lines and fixes (replacements of spans, for the editor). Spans are byte offsets inside the engine; `Diagnostic::record` gives the form that leaves the engine, with a 1-based line and a 1-based column counted in Unicode scalar values (Language Reference, section 3.8). The JSON text of that record arrives with `--format json` in 0.2.0; the language server converts columns to UTF-16 units in 0.7.0. `Diagnostics` collects what a stage finds, so `zeff check` can report every error.

**Reason.** Engine Specification, section 8.3, point 1: a diagnostic is data on the IR, printed, underlined and shown by Zemp from one record.

## 18 October 2026: How a diagnostic is printed

**Choice.** The renderer follows the printed examples of Language Reference section 11 exactly: header `error[Z0101]: message`, an arrow line ` --> file:line:column` that always begins with one space (every example of the specification does, whatever the width of the line numbers), a gutter as wide as the largest line number shown, source lines with right-aligned numbers, `^` under the primary span and `-` under secondary ones, `...` between lines that are not adjacent, and `= help:` lines after an empty gutter line. A label across several lines is drawn to the end of its first line. Several labels on one line each get their own marker line. A tab is shown as four spaces. Columns are scalar values, so the markers misalign under characters a terminal draws double-width; that is accepted for now. A diagnostic with no file prints the header and its help lines only. The short form under a result (`warning: 211 rows with NA in lwage ... (line 21)`, section 10.2) is not this form and is produced by the interpreter when it prints results.

**Test.** `tests/spec_examples.rs` reads the ten printed errors from the Language Reference (sections 3.6 and 11), rebuilds each as data, and requires the printed text to match the specification exactly; it also fails if the specification gains an eleventh example the test does not build. Nine matched at once; the tenth exposed a slip in the specification (logged in `docs/spec_changes.md`, the first entry).

**Reason.** The specification is the authority on message layout (printed layouts are stable within an edition). Reading the examples from the specification itself rather than copying them stops the test and the text drifting apart. `insta` (named in the testing handbook) is not added yet: exact comparison with the specification is stronger here, and `insta` comes with the first tests that snapshot output the specification does not print (the parser's trees and messages, step 7).

## 18 October 2026: The lexer, its tokens and its recovery

**Choice.** `zeff-syntax` lexes a whole file into tokens and never stops at an error. Everything it cannot read becomes an `Error` token plus a diagnostic, so every byte of the input is in a token, whitespace or a comment (a property test checks this on random text), and the parser can go on and report its own errors; later stages skip `Error` tokens without a second message. Names, the 26 reserved words, `_` alone, numbers, strings, raw strings, doc lines, all punctuation and the operators of section 3.3 are tokens. An `Int` token holds its magnitude as a `u64`: 2^63 is kept, because `-9223372036854775808` is legal only with its minus sign, which the parser checks; only a number beyond 64 bits is refused here (Z0310). `0.1` and every Float literal are parsed with Rust's correctly rounded `str::parse`, so a literal is the same number on every target. A byte-order mark at the start is skipped; a CRLF file lexes exactly as the LF file (property-tested); a tab is whitespace.

**Line breaks (section 3.1).** The lexer keeps a stack of open brackets; the innermost decides what a line break means. `(`, `[`, a record literal and the body of `case` ignore line breaks; a block, `model { }` and `dag { }` end a statement or line. A `{` is classified from the token before it: after `case`, `model` or `dag` it opens that; after something that ends an expression or a type (a name, a number, a string, `)`, `]`, `}`, `?`, `else`, `true`, `false`, `NA`, `Inf`) it opens a block (`if x {`, `fn f() -> Float {`); after `=>` it is a record when what follows is `}`, `..` or `name:`, and an arm's block otherwise; anywhere else a record. A line break makes no NEWLINE when the line ends with a comma or a binary operator, `=`, `=>`, `->`, `::` or `as`; when the next line that is not blank or a comment begins with `.` and a name (not `..`); when it follows a blank or comment-only line; or at the start of the file. One NEWLINE is always supplied at the end of the file. A line may not end with `.` (Z0312). `--` is an edge only inside `dag { }`; elsewhere it is two minus signs. A `///` line alone on its line makes no NEWLINE after it, so doc lines and the `fn` below are adjacent tokens as the grammar writes them (`{ DOC } "fn"`); whether they really sit directly above a function (Z0318) is the parser's check. `// zeff:` comments are kept in a separate list, not in the token stream; their checks come in 0.7.0.

**Messages.** Z0310 (malformed numbers: `.5`, `5.`, leading zero, misplaced `_`, an exponent without digits, a number run into a name such as `0x10`, too large), Z0311 (unknown or malformed escape, string never closed), Z0312, Z0315 (`;`, `&`, `%`, `**`, `<-`, `TRUE`, `FALSE`, `NULL`, `None`, and single-quoted text, each with the Zeff form in the help line), Z0302 (a bracket never closed; the message names the first later line where a new statement seems to begin, which reproduces the specification's example exactly). Three conditions have no number in the specification: an unexpected character or an unclosed or empty backtick name (provisionally Z0301), an unmatched closing bracket (Z0303). They are recorded as open decision #41 with the number proposed for the construct that 0.1.0 parses but does not run (Z0304, used from step 7). The messages are snapshot-tested in `crates/zeff-syntax/tests/snapshots/`.

**Reason.** Section 3 and the freeze: the lexer follows the text; where the text is silent a provisional answer is chosen, recorded, and put to the owner as an open decision with a deadline instead of being written into the specification.

## 18 October 2026: The parser accepts the whole grammar

**Choice.** `zeff-syntax` parses the entire grammar of section 3.4: `use`, `fn` with doc lines and every kind of type, `let`, `for` (also as `[for ...]`), `return`, `break`, `continue`, `if` and `else`, `case`, `model { }` and `dag { }` blocks, calls, method chains, indexes, records, lists, mappings, ranges and all the operators of section 3.3. The tree (`ast`) has a node for each, with a span on every node. Whether a release can run a construct is not the parser's concern: the checker (step 12) refuses what 0.1.0 does not run, with the code Z0304 of open decision #41. Parsing everything lets the specification's own scripts (the 281-line sample and the complete analysis of section 10) serve as full-grammar tests, and no later release changes the parser to add syntax.

**Reason.** Section 3.4 is normative for syntax, and the grammar is designed for the whole language. A parser that refused constructs would have to be reopened in 0.5.0; a checker that refuses them is the only code that changes.

## 18 October 2026: Operators, associativity and the checks done in the parser

**Choice.** Levels 4 to 9 and `as` are parsed by one precedence-climbing loop; `^` and the prefix operators are handled in one operand routine, so `-2^2` is `-(2^2)`, `2^3^2` is `2^(3^2)`, and `2^-3` is allowed (as the grammar's `power = postfix ["^" unary]` says). Comparisons, ranges and formula operators do not chain (Z0314; the second operator is reported and parsing goes on). `-9223372036854775808` is one literal and the only way a number above 9223372036854775807 is accepted (Z0310 otherwise, including `-9223372036854775808^2`, where the minus does not apply to the literal alone). The parser also reports: a statement that begins with an operator (Z0305), `as`, `=~` and `~~` outside a model block (Z0308), `fn` and `use` out of place (Z0309), `return`, `break` and `continue` out of place (Z0313), `|` and a misplaced `=` (Z0315), `_` not last in a `case` (Z0316), a `///` line not directly above a `fn` (Z0318), and nesting beyond the limits (Z0307). Z0306 (`:` outside a formula), Z0321 and Z0322 depend on the parameter's type and belong to the checker. After an error the parser skips to the end of the statement and carries on, so every statement's mistake is reported; a token the lexer already reported (and the end of the file inside an unclosed bracket) gives no second message.

**Reason.** Section 3.3 says the grammar needs no knowledge of function signatures, so the parser builds one tree for every argument and the typed IR gives it meaning. A property test builds random operator expressions, prints each with the fewest parentheses by a precedence table coded separately, and requires the parser to rebuild the generated tree exactly (4,000 cases, each way).

## 18 October 2026: Nesting limits and the stack (section 3.8, "Limits")

**Choice.** 256 levels of expression and `for` nesting, and 1,024 steps in one chain (calls, fields, indexes) or one run of operators at a level, are enforced with Z0307. Prefix operators and operator runs are handled by loops, so no input makes the parser recurse beyond 256 levels. Measured stack needs at the limit, in a release build: parentheses 545 KiB, calls 689 KiB, lists 545 KiB, nested `if` 897 KiB, `for` 321 KiB (debug builds need about four times as much). The checker and interpreter recurse over the same tree. So the budget is: the WebAssembly engine is linked with an 8 MiB stack (instead of the default 1 MiB, with `-C link-arg=-zstack-size=8388608`, set when the engine's WebAssembly build is wired in at step 13), and the native engine runs on a thread of its own with a stack of at least 64 MiB, as the engine worker of section 8.3, point 7 does anyway. A release-mode test (`crates/zeff-syntax/tests/stack_limits.rs`, run by the continuous-integration job `test`) requires every kind of nesting to parse within 2 MiB at 255, 256, 257 and 2,560 levels, so growth in the parser's stack use is caught. The tests in debug mode run on a 64 MiB thread.

**Reason.** The limits exist so that the parser's stack is bounded in WebAssembly. The measurement showed the default 1 MiB is too close to the parser's need alone, so the build gives more stack and a test guards the figure. Reducing the frames further would mean reshaping the tree, which is not worth it now; `Expr` is 88 bytes.

## 18 October 2026: One brace token becomes two

**Choice.** The lexer emits `LBrace` for a record literal or record type and `LBlock` for a `{` that opens a body (a block, the arms of a `case`, a `model { }` or a `dag { }`), because it already had to tell them apart to decide what a line break means. The parser relies on this to tell an arm's block from a record after `=>`. A `{` after `>` (the end of a type such as `List<RegFit>`) opens a body.

**Reason.** One decision made in one place; found when the specification's own function example failed to parse.

## 18 October 2026: The engine reads files through an interface

**Choice.** The engine never calls `std::fs` itself. It uses the `FileSystem` interface (read, list, canonicalise, create, write, remove): `StdFileSystem` for the machine, `MemoryFileSystem` for tests and for the browser, where the user grants a folder once and a file system supplied from JavaScript will stand behind the same interface (step 13). Project discovery, the path rules and `zeff new` all work through it.

**Reason.** The same engine must run natively and in WebAssembly, where there is no `std::fs`; adding the interface later would mean rewriting code and tests that already pass. It also makes most tests in-memory and fast, with a few on a real folder for what only a real disk shows (case and links).

## 18 October 2026: `zeff.toml`, the project file

**Choice.** `zeff.toml` is read with the `toml` crate 1.1.8 (default features off, `parse` and `std` only, so no serde), which keeps the position of every value, so each message points at the value that causes it. All problems are reported at once, in the order of the file. Unknown keys and tables are errors (with "did you mean" for near misses), not warnings. `[project]` needs `name`, `zeff` (one exact version of three numbers, with an optional pre-release tag so that a development build, `0.1.0-dev`, can pin itself; `^0.1` and the like are refused with the exact form suggested) and `edition`; `memory` is a number with KB, MB or GB, kept as written until the memory budget arrives (0.7.0); `network` is true or false. `edition = "preview"` is the only edition before 1.0.0; `"2027"` and anything else give Z0706 (exit code 4). `[data]` takes name = { path = "..." }; the names are letters, digits and `_`, and `zeff` is reserved for the built-in data root of 0.2.0. `[packages]` must be empty before 1.0. Two codes the specification does not give — a file that is not valid TOML (Z0712) and a file that is wrong for Zeff (Z0713) — are used provisionally and put to the owner as open decision #42 (Z0704 and Z0705 are taken by the memory budget and by cancellation).

**Exit codes.** Z0706, Z0710 and Z0703 are exit code 4 (the engine, edition or lock does not match the project); every other problem in the project, the script or the way a command was typed is exit code 1; 2 stays for internal errors. A mistake in how a command is typed is the user's to fix, so it is a 1 and not a 2.

**Reason.** Section 2 and section 3.8 of the Language Reference; a copied project must re-run unchanged, so nothing in its file may be ignored silently.

## 18 October 2026: Finding the project, the pin, and the commands of this build

**Choice.** `zeff` walks up from the current folder to the nearest `zeff.toml`; outside a project `run`, `check`, `fmt` and `test` stop with Z0709 and exit code 1. The project must pin exactly the running engine (Z0710, exit code 4), because before 0.9.0 launcher and engine are one binary and cannot install another; the message says that installing engines arrives with 0.9.0. `zeff new <name>` makes `zeff.toml` (pinning the running version), `scripts/main.zeff` (comments only), `data/` and a `.gitignore` that leaves out `.zeff/cache/`, `.zeff/fetched/`, `.zeff/runs/`, `.zeff/open.lock` (the lock file that stops a project being opened twice; its name is mine, the specification says only "a lock file in `.zeff/`"), `.zeff/session.zeff`, `.zemp/views.json` and `data/`; it never touches an existing folder and removes what it made if it fails half-way. A project name is lowercase letters and digits with `_` or `-`, starting with a letter or digit, in at most 64 characters, with the corrected spelling suggested. `zeff version` prints `zeff <version>`. `run`, `check`, `fmt` and `test` find and check the project and then say that they are not available yet; the commands the specification lists for later releases say the same; anything else is an unknown command. The flags (`--project`, `--color`, `--format`, `--quiet` and the rest) arrive with 0.2.0 as section 14 says.

**Reason.** Section 2 and the 0.1.0 row of section 14. The placeholder messages are temporary: steps 12 and 13 replace them.

## 18 October 2026: The path rules

**Choice.** A script's path is a string written with `/`, from the project folder. It is refused (Z0701) if it is empty, uses `\`, is absolute (`/x`, `C:/x`), climbs above the project with `..`, or leaves it through a symbolic link; `root:file` reads under a declared data root (relative roots are relative to the project), and an unknown root, a `..` or an absolute path after the root's name is refused as well. Each part of a path is compared with the folder listing, and a part that differs only in case from a real file is Z0702, with the real spelling suggested, on every system. A write (`save`, `export`) must land under the project folder; a data root, an absolute path, `..` out of the project, a link out, an empty path or the project folder itself is Z0707. The message for a path outside the project reproduces the specification's own example exactly (tested against the text).

**Reason.** Section 2, "Paths from the root", "Data roots" and "Writes"; Language Reference section 3.8, "Paths". Two real-disk tests (case and a link) cover what the in-memory file system cannot.

## 18 October 2026: Columns, and the only place Arrow is touched

**Choice.** `Column` is a struct whose Arrow storage is private; the seven types of section 3.8 are stored as Boolean, Int64, Float64, LargeUtf8, Date32, Timestamp(microsecond, "UTC") and Dictionary(Int32 → Utf8), as the specification's table says (a test compares each stored type with the table). Other crates see Rust values: typed iterators (`as_ints()` and the like, `None` for another type), `get(row)` as a `Value` (including `Value::Na`), `slice` (shares the buffers), `levels`/`as_codes`/`as_labels` for categories, and `numeric_values()`, which gives the valid values of a Float, Int or Bool column as Floats and the number missing, the form `mean` and `sd` need (an Int beyond 2^53 loses exactness, section 3.7). Missing values are the validity bitmap. `Column::floats` turns every `NaN` into `NA` and returns how many it converted, so the caller reports the count once with the cause (section 4.1); `Inf`, `-Inf` and `-0.0` are kept bit for bit. A category is built from its levels in order and 0-based codes; duplicate levels and codes beyond the levels are refused. `Table` is named columns of one length; only exactly equal names clash (names that differ in case are the reader's concern, section 3.6). Three-valued logic (`and`, `or`, `not`) is in the kernel and is tested against the specification's truth table, row by row and mirrored.

**Enforcement.** `cargo run -p xtask -- check-tiers` now also fails when any crate except `zeff-columns` depends on `arrow`, an `arrow-*` crate or `parquet` (test-only uses excepted); it was shown to fire on a real violation. This is the "thin layer" of risk R6: an upgrade of Arrow changes this crate and nothing else.

**Left for later.** The category's ordered flag and contrast, and the other column metadata (labels, units, missing codes), come with the metadata store in 0.4.0; selection vectors and shared columns with 0.6.0; the identity relation used by `sort` and grouping (`NA` identical to `NA`, `-0.0` to `0.0`) with 0.2.0. The reducers' NA rules (skip and count, `Inf`, all-missing) are applied by the functions that use `numeric_values()`, with the numeric kernel's results (steps 20 and 21).

## 18 October 2026: The dates kernel crate

**Choice.** `kernel/zeff-dates` is the "date parsing" module of section 8.1, rule 8: the proleptic Gregorian calendar for years 1 to 9999 (Hinnant's algorithms, integer arithmetic only), days since 1970-01-01 and microseconds since 1970-01-01 00:00:00 UTC, strict ISO 8601 reading (`YYYY-MM-DD`; `YYYY-MM-DDTHH:MM[:SS[.f]]` with `T` or a space between date and time, as RFC 3339 allows and as R writes, a fraction of up to nine digits kept to the microsecond, and `Z` or an offset applied to reach UTC), ISO printing, and formats in `strftime` notation with the directives `%Y`, `%y` (69–99 as 1969–1999, 00–68 as 2000–2068, as POSIX does), `%m`, `%b`/`%B` (English month names, any case), `%d`, `%H`, `%M`, `%S` and `%%`; white space in a format matches any white space; a format must have a year, a month and a day, may not repeat a directive, and may not have a minute or second without an hour. No format is ever guessed.

**Reason.** Language Reference, section 3.8 ("Time") and 4.1 ("Import"): the reader needs the calendar now, and the `time` package of 0.6.0 will use the same crate. Every day of the calendar round-trips (tested in full at a stride, and by property).

## 18 October 2026: The CSV reader and its rules

**Where.** `packages/tier1/data/src/csv.rs`, with the `import` function it serves; the reader interface of section 6.1 (`sniff`, `schema`, `read`, `options`) is given as plain functions (`read_csv`, `csv_schema`) and is made a trait when the second reader arrives (0.11.0). The whole file is held in memory while it is read; streaming is 1.1.

**Rows.** A row is numbered as a text editor numbers lines: the first line of the file is row 1, skipped lines and the header count, and a record with a quoted line break is numbered by its first line. This is what `sed -n '14207p'` and every editor show; Excel's row number agrees unless a value holds a line break.

**Lines.** `skip:` drops that many physical lines before anything is read. A line that is empty or white space only is skipped and counted in a note (R and pandas skip them; "nothing disappears silently" asks for the count); a quoted empty value, `""`, on a line of its own is a row with a missing value. A delimiter at the end of a line ends an empty last field. The delimiter is `,` unless `delim:` is given; when the first line has no comma outside quotes but has `;` or tabs, the more frequent of the two is used (a tie goes to `;`) and a note says so. Quoting is RFC 4180 (`"`, doubled inside, line breaks allowed inside) and lenient where RFC 4180 is silent: a quote inside an unquoted field is a character, and text after a closing quote is kept, as most readers do; a quote never closed is Z0607 naming the row it opens on; a row with another number of fields than the header is Z0607. A byte-order mark is removed with a note; a row that is not UTF-8 is Z0608 naming the row (`encoding:` arrives in 0.2.0, and the message says so).

**Names.** With `header: true` the first non-blank row names the columns and the names are kept exactly as written, spaces included (`names: keep`); an empty name, two equal names, or two names that differ only in case are Z0605. `header: false` names them `v1`, `v2`, …. `names: snake` lowercases, splits `camelCase` and runs of capitals as R's `janitor` does (`GrossSales` → `gross_sales`, `GDP growth` → `gdp_growth`), strips accents through NFD (`café` → `cafe`), turns every other character into `_`, collapses runs, puts `x` before a leading digit (`2024` → `x2024`) and names an empty result `v<position>`; two headers that become one name are Z0605 ("snake clash"), and a note lists every name that changed. An empty file is Z0605 ("no header line").

**Missing values.** A cell is missing when its trimmed text is empty, `NA` or `.` (exactly; `na` and `N/A` are text), or one of the `na_values:`, matched as text and, when both are numbers, as numbers (`-99.0` matches `-99`); a note per column says how many values each code removed. `NaN` in any case becomes `NA` with a note; `Inf`, `-Inf`, `inf`, `infinity` (any case) are infinity, so files from R and Python both read.

**Types.** Guessed from the first 1,000 data rows, in this order: Bool (`true`/`false` in any case; `0` and `1` stay Int), Int (an optional minus and digits, within 64 bits; no `+`, no `_`), Float (Rust's own parser on digits, sign, point and exponent, plus the infinity and NaN words; `1,000` and `1,5` are text until `thousands:` and `decimal:` arrive in 0.2.0), Date (strict ISO), DateTime (ISO as above), otherwise Str; a column with nothing to guess from is Str; an impossible date such as `2026-02-30` makes the column Str. ISO dates are read as `Date` from this release, although the `time` functions arrive in 0.6.0, so that no column changes type between releases. A value after the first 1,000 rows that does not fit is Z0606 naming the row, the column and the value, exactly as the specification prints it; a whole-number column meeting `3.5` is Z0606 suggesting `types: {n: Float}` rather than widening silently. `types:` declares a column's type (Bool, Int, Float, Str, Date or DateTime, the last two with an optional format); a declared column's every value must fit (Z0606 with "declared by `types:`"), a declared column that the file lacks is Z0101 with "did you mean", and a declared text column gets no date note. A text column whose values all look like dates in one non-ISO shape (three numbers between one separator with a four-digit year first or last) gets a note with three examples and the `types:` entry to write; the day-first or month-first form is proposed when a value settles it (a first number above 12 means day first), and both are offered otherwise. A `DateTime` with `Z` or an offset is converted to UTC and counted in warning W0702. A text column holding two values that differ only in Unicode normalisation form (NFC compared) is warning W0601 with the pair. Text keeps its spaces; only the missing markers, numbers, words and dates are recognised trimmed.

**Reference.** `tests/reference/csv_cases.py` writes 17 files (quoted line breaks, doubled quotes, CRLF, no final line break, a byte-order mark, `;` and tab delimiters, Unicode and awkward headers, empty fields, trailing delimiters, blank lines, one column, spaces, a quote inside an unquoted field) and the fields Python's `csv` module reads from each; the Rust test requires the same fields. Blank lines are filtered on both sides, since Python returns them and the reader skips them.

## 18 October 2026: The function registry and where the help check runs

**Choice.** `kernel/zeff-registry` holds the function registry (section 8.1, rule 8). A package registers each function as a `FunctionSpec`: name, package, whether it is written in method form (`data.mean(var)`; the first parameter is then the receiver), the parameters (name, type as the language writes it, default, and whether the usage line writes it as an option), the return type, the diagnostics it can raise (code and when; a note has no code), the text of its help file (`help/<name>.md`, compiled in with `include_str!`, so a missing file fails compilation), and its conformance record once it has one. `Registry::build` checks every function against the catalogue (`docs/spec/zeff_functions.csv`, compiled into the engine) and its page, and refuses the whole registry if anything is wrong: a function without a catalogue row, a function registered twice, a parameter the catalogue's usage does not list, or any fault in the page. The engine builds the registry when it starts, so an engine with an incomplete page does not run, and `cargo test` builds it too, so continuous integration fails first. That is how the build check of section 9.1 is realised; a true compile-time check would need the packages as build dependencies of the engine, compiled twice (once for the build machine), which is too slow for the browser cross-build.

**The catalogue cross-check.** Every registered parameter must appear in the catalogue's usage for that function, with two exemptions the catalogue's own style requires: the shared arguments of section 6, which the catalogue does not repeat, and parameters of type `Formula`, which the catalogue writes as `y ~ x`. A namespaced name such as `dist.normal` is a name, not a receiver. The reverse check (a catalogue parameter not yet registered) is not an error, because `import` registers in 0.1.0 only the options that work (decided in the release checklist).

**Reason.** Section 8.1, rule 1 and section 9.1: one source, four views; "a function without a complete page does not exist".

## 18 October 2026: The help file format

**Choice.** A help file is Markdown with the function's name as its title (`# mean`) and the written parts of section 9.1 as level-two headings: `Summary` (one line under 80 characters, no full stop, completing "mean — …"), `Description`, `Arguments` (one bullet per parameter, `- name: text`, continued on indented lines; a shared argument may have no bullet or one extra sentence, since its text comes from the shared table), `Value`, `Details` and `References` (required for the closed-form, distribution, iterative and stochastic accuracy classes, which the catalogue gives), `See also` (names separated by commas, each a catalogue name or `name:` of a shared argument), and `Examples` (a run of `> ` lines is a statement, the lines after it are what it prints, a blank line separates examples). Paragraphs, inline code in backticks and bullet lists are the only markup, kept as written. Writing a generated part (Usage, Warnings and notes, Accuracy, Availability) is an error, as is an unknown or repeated heading, an entry naming no parameter, a parameter without an entry, an empty required part, or a page without an example. Running the examples is the example runner's job (step 14).

**Reason.** Section 9.1 ("Sources"): the parts above as headings, paragraphs, code and bullet lists; the same content as the `///` form, which the parser already lexes.

## 18 October 2026: The printed page

**Choice.** The page follows `docs/spec/zeff_help_examples.md`: a header line of 118 columns with `name — summary` at the left and `package · tier N · since <release> · 1.0 · <accuracy class>` at the right (`1.0` for a function planned for 1.0, `roadmap` otherwise); then USAGE (generated from the signature; a usage longer than the line breaks after a comma, with the continuation under the first argument), DESCRIPTION, ARGUMENTS (`name` or `name:` in a column two wider than the longest name and at least twelve, then `Type = default. meaning`; a shared argument takes the meaning of the shared table, followed by the function's sentence if any, and ends with `(shared)` at the right margin), VALUE, DETAILS if written, WARNINGS AND NOTES if any diagnostic is declared (`Note` or the code, then when), ACCURACY (`Exact.`, or `Closed form: <reference>. Last run: <record>.`), REFERENCES if written, SEE ALSO, EXAMPLES (`> ` lines, then output). Text wraps at 108 columns. The examples of the specification were wrapped by hand at no single width (their header lines are 118 columns in three pages and 120 in one), so the renderer reproduces their header and usage lines exactly and every word of every part in order, which the tests check for `where`, `merge` and `attempt`; the line breaks inside a part are the renderer's own and are kept as snapshots.

**Reason.** The layout of section 9.1's examples; a greedy wrapper is deterministic, which hand wrapping is not.

## 18 October 2026: The typed IR and the checker

**Choice.** `crates/zeff-ir` lowers the syntax tree to a typed IR: a list of statements (`let`, or a statement that prints its value), each expression carrying its type, every call resolved to a package's function with its arguments in parameter order (`None` where an argument was omitted), and open-ended arguments (`print`'s values, `frame`'s definitions) kept apart. Names are resolved as section 3.7 says: a name in call position is a function; where the parameter takes a `Var` or `Vars`, a bare name (or a list of bare names) is a variable, left as a name because the schema pass arrives with 0.6.0, so the interpreter resolves it against the frame and raises Z0101 or Z0102 then (`zeff_ir::messages`, tested against the specification's two examples); where the parameter lists words, a bare name is checked against the list (Z0402; text in quotes is Z0403); anywhere else a bare name is a binding (Z0101, with "did you mean" among the bindings, or a hint when the name is a function). A method `x.f(args)` is looked up by the receiver's type among the functions called `f` (one home per name per type); `package::f` by the package. Arguments are matched as section 3.1 says: positional in parameter order, options included, then named; once named, the rest must be (Z0408); unknown (Z0404), repeated (Z0405), missing required (Z0406: a parameter is required when it is not an option), too many (Z0407). Each argument is lowered with its parameter's type as context, so `NA` and `[]` take their types from it (and are Z0219 without one), a list joins its element types (Z0214 when they do not), and the types are then compared (Z0401; an Int fits a Float, a `Column<Int>` a `Column<Float>`, one name a `Vars`). `Nothing` cannot be bound or passed (Z0206); a `let` may not reuse a `core` name (Z0105) and warns when it hides another package's function (W0101). `Date("...")` and `DateTime("...")` are type constructors whose format is checked at once (Z0409). A negative numeric literal is a literal; every other operator, and `fn`, `use`, `for`, `if`, `case`, `[for]`, indexing, fields, mappings, ranges, formulas, `model`, `dag`, `as`, `.` and spreads, are Z0304 naming the release that brings them. Every statement is checked and every error reported; an expression that failed is typed `Unknown`, which no later check reports again, so one mistake gives one message.

**The codes.** The specification gives most of these conditions no number; the free numbers used are put to the owner as open decision #43 (Z0103, Z0105, W0101, Z0401, Z0404 to Z0409) and #44 (W0201, W0204, for the reducers' warnings declared on `mean`'s page).

**Reason.** Section 8.3, point 1, and section 11 ("`zeff check` runs only this stage, and reports every error it finds, not only the first").

## 18 October 2026: `zeff check`, and which functions are registered when

**Choice.** `zeff check [script]` opens the project, resolves the script's path by the path rules (default `scripts/main.zeff`; a script the project does not have is Z0714, added to open decision #42), parses and checks it, prints every diagnostic to standard error in the order of the text, then one line: `checked scripts/main.zeff: no problems`, or `scripts/main.zeff: 5 errors, 1 warning`; the exit code is 1 when there is an error, else 0. A registry that fails to build is an internal error (Z9001, exit code 2). The engine's registry is assembled from the packages when the engine starts; a function is registered when it runs, so the example runner of step 14 never meets an example that cannot run: this step registers `import`, `mean` and `print` with first drafts of their pages (their bodies are step 13), and the other seven register at their own steps. The checker's own tests use a fixture registry of all ten signatures.

## 18 October 2026: Values, the display interface and the calling convention

**Choice.** `zeff-core` declares the values a running script holds (`Value`: Nothing, NA, Bool, Int, Float, Str, Frame, List, Record, and the argument-only Var, Vars, Word and Type), the display interface (`display::show`, the printing rules of section 3.8), and what a function body receives (`runtime::CallContext`: the files it may read through the `Files` trait the engine implements, the script's name, the spans of the call and its arguments, the statement's output buffer and its message list; `Args`: the evaluated arguments in parameter order, with the open-ended values and definitions apart). A body is a plain function returning the value or the boxed diagnostic that stops the script. Each package returns `Vec<Function>` (specification and body); the engine registers the specifications and keeps the bodies by package and name. A `Frame` holds its table behind a reference count, so a frame bound twice is not copied, and carries the name it was bound to, which its printed header and its messages use (`no variable `incme` in `poll``; `the frame` when it has no binding).

**Printing.** A Float prints to six significant digits with trailing zeros dropped, in exponent form below 1e-4 and from 1e15, written as R writes it (`9e-05`, `1e+15`); a value of a million or more keeps every digit before the point and rounds to a whole number, as R does, rather than losing digits before the point, which "six significant digits" read literally would do; `-0.0` prints `0`. Lists and records print one line per item up to 20, then `… and N more items`. A frame prints its header, `wages · 18,412 rows × 13 variables`, and will print its first ten rows from step 19. The rounding question (what `1234567.891` prints) is one for the owner at step 19; R's behaviour is the default until then.

**Reason.** Section 8.1, rules 4 and 5; section 3.8. The engine's own file access stays out of `core` because `core` depends only on kernel crates.

## 18 October 2026: The interpreter and `zeff run`

**Choice.** The interpreter runs the IR statement by statement: a `let` binds (and names a frame); any other statement prints its value through the display interface; a call evaluates its arguments in the order written, receiver first, which the IR now records, then calls the body. Warnings and notes a statement raises print under its output in the short form of section 10.2, `warning: 1 row with NA in hours was skipped (line 2)`, without a code (open decision #45); the first error stops the run and is printed in the full form with its position. `zeff run` prints the script's output on standard output and everything else on standard error; a check-time error stops the run before anything prints, and only the first is shown, as section 11 says of `zeff run`; the exit code is 0, 1 for an error in the script, 2 for an internal error (Z9001, such as a function without a body). The command runs on a thread with a 64 MiB stack. The messages `no variable` (Z0101, Z0102) and `wrong column type` (Z0401) moved from the IR crate into the diagnostics kernel crate, because the `data` package raises them at run time and a package may depend only on kernel crates. A path inside the project with no file is Z0715 (added to open decision #42). `import`'s `types:` names a column by the name the script will use or by the header as the file writes it, so `names: snake` does not break a declaration.

**The milestone.** `let wages = import("data/wages.csv")` then `wages.mean(wage)` prints `24.5333` through the lexer, parser, checker and interpreter. The conformance report has three new lines for it (the digests of the script's standard output and error and its exit code, on an in-memory project), so the four-target identity check compares the whole engine from this step; the WebAssembly build is linked with an 8 MiB stack (`-C link-arg=-zstack-size=8388608`, as decided at step 7) and gives the same bytes as the native build under Node. The browser bundle now holds the whole engine: 330 kB compressed, a 23 ms cold start.

**Reason.** Sections 2 and 8.3; Language Reference sections 3.1, 3.7, 3.8, 10.2 and 11; risks R2 and R4.

## 18 October 2026: The example runner

**Choice.** `zeff_engine::examples::run_examples` runs every example of every registered function and compares what it prints with what its page says. The examples of one page run as one script, in order, because later examples use the bindings of earlier ones (the specification's own pages do this); each example is compared with the output of its own statements, their warnings and notes included, as the interpreter prints them: the value first, then its messages, which is section 10.2's "under the output they belong to" (the `where` page of the help examples shows a note before a value; section 10.2 is normative and is followed). ## 18 October 2026: The reference and edge-case harness

**Choice.** `tests/reference/functions.py` writes two committed things: the fixed datasets of `tests/datasets/` and `tests/reference/functions.json`. The twelve datasets are the ordinary ones (`wages`, three rows; `wages_large`, 1,200 generated rows with a Bool, Unicode region labels and 5% missing hours) and the edge cases of the testing handbook, section 1: `all_na`, `one_row`, `zero_variance` (a constant, a constant with a gap, a constant near 1e9), `empty` (a header alone), `infinities` (`Inf`, `-Inf`, both, `NaN`), `magnitudes` (an offset of 1e9, sixteen orders of magnitude, subnormal numbers), `bools` (mixed case, missing), `guess_boundary` (1,001 rows whose last breaks the guessed type, so it needs `types: {hours: Str}`, recorded in the reference as the dataset's import options), `awkward_names` (headers with spaces, brackets, a digit first, CJK, two names differing only by a suffix, and one holding a backtick, which no script can write and `names: snake` is for) and `unicode_labels` (accents in both normalisation forms, an emoji, CJK). ## 18 October 2026: `sd`, and scaling in the kernel's variance

**Choice.** `sd` has the shape of `mean`: the sample standard deviation with divisor n − 1 over the non-missing values, which are skipped with W0201. What makes it undefined is reported with W0205, the specification's code for a result that is `NA` because of `0/0` or `Inf − Inf`, with the cause named: one value left ("sd needs at least two values, but x has one"), an infinite value ("x holds an infinite value"), or squared deviations that overflow. A constant column gives exactly `0`. No new code was needed, so open decision #44 is unchanged.

**The kernel.** The reference found that `sd` of the `tiny` column of `magnitudes.csv` (values near 1e-301) printed `0`, because the squares of the deviations underflow. `zeff-numeric` now scales the deviations by a power of two that puts the largest in [1, 2) before squaring, and undoes the scale afterwards (`variance` divides by the square of the scale; `sd` takes the root first and divides once, so that a standard deviation whose square underflows is still right). Scaling by a power of two is exact, so for ordinary values the result is bit for bit the unscaled one: the 36 numeric cases of the conformance report did not change. The scale is read from the number's exponent bits, not from a logarithm, keeping the result-bearing path free of library maths (Engine Specification, section 8.3). The same scaling protects values near 1e200, whose squares overflowed before.

**Definition of done (testing handbook, section 4).** Reference: every numeric column of every dataset against Python's `statistics.stdev` (24 columns; closed form at six significant digits). Edge cases: one value, two values with one missing, all missing, no rows, a constant at three magnitudes, the four infinity columns, a Bool column, the large file, the offset and tiny magnitudes. Properties: the sd of integers is the exact sd rounded (computed in 128-bit integers); shifting leaves it, scaling multiplies it by the absolute factor, reversing the rows changes nothing; two values have sd |a − b|/√2. Snapshots: every run-time and check-time message. Identity: the milestone script takes five standard deviations. Help page complete with details and references, examples run.

**Reason.** Language Reference, section 4.1 (Statistics) and section 11 (W0205); Engine Specification, section 8.3 (numerical methods); the catalogue row for `sd` (closed form).

## 18 October 2026: Expressions over columns

**Choice.** A column is a value, `Value::Column`, holding the Arrow column itself: `wages["wage"]` takes it from a frame (Z0101 with the frame's name and a suggestion when the name is wrong; a bare name between the brackets gets the hint to quote it), and every operator of section 3.3 applies to it row by row, a scalar beside it standing for its value in every row. ## 18 October 2026: The maths kernel

**Choice.** `zeff_numeric::maths` holds the elementary functions behind one pure-Rust implementation: `exp`, `log`, `log2`, `log10`, `log1p`, `expm1`, `sin`, `cos`, `tan`, `asin`, `acos`, `atan`, `atan2` and `pow` from the `libm` crate (0.2.16, MIT and Apache-2.0; a port of musl), `sqrt`, `floor`, `ceil` and `trunc` from Rust's own intrinsics, which are exact IEEE operations on every target. Rounding is decided on the exact binary value, as R decides it: `round(2.675, 2)` is 2.67 because the stored number lies below the tie; a true tie is detected exactly from the bits (`x = M·2^E` with M odd is a tie at `digits` decimals when `E = −(digits + 1)`), and broken to the even neighbour (R, the default) or away from zero (Stata and Excel, `mode: away`), the decimal chosen being formatted and read back so the result is the nearest double. `round_significant` turns significant digits into decimals from the exact decimal exponent. `div_int` and `mod_int` are floored division and its remainder with the sign of the divisor, as Python and R (`i64::MIN div -1` is the one overflow; `mod` by −1 is 0); `div_float` and `mod_float` follow `/` at zero. **Reference.** `tests/reference/maths.py` writes `maths.json`: Python's `math` (the platform's C library) on a 58-point grid, `atan2` and `pow` tables, the roundings of 30 numbers at six digit counts half to even (Python's `round`) and half away (the `decimal` module's ROUND_HALF_UP on the exact value), significant digits, and floored divisions of Ints and Floats. The kernel must agree exactly where the answer is exact (whole numbers, zeros, infinities) and within two units in the last place elsewhere, since two correctly implemented libraries may differ by one; the roundings and divisions agree exactly. Python raises at `log(0)` where section 4.1 wants `-Inf`, so the script writes Zeff's answer there. R takes over as the main reference at step 10.

**Identity.** The conformance report gains seventeen `maths/*` lines: every function on the grid, the powers, the angles, the roundings in both modes and the divisions, so the four native targets and WebAssembly prove the kernel gives the same bits everywhere.

**Tests.** Unit tests of every rule; the reference tests; properties: `log(exp(x)) = x`, `sin² + cos² = 1` and `√x² = x` within a rounding, rounding idempotent and within half a unit of the exact value, floored division and remainder recompose the dividend with the remainder's sign that of the divisor.

**Reason.** Language Reference, section 3.7 ("Numbers"), 4.1; Engine Specification, sections 8.3 (point 3) and 13; the catalogue rows of `round`, `div` and `mod`.

## 18 October 2026: The command-line options, `zeff eval`, the console and the scratch project

**Options.** The options of section 2.1 that this release has are read from anywhere on the line, before or after the command, as `--name value` or `--name=value`: `-p`/`--project <dir>` (the folder the project is looked for from; not a folder is a usage error), `--format text|json`, `--color auto|always|never` (`--colour` accepted; `auto` means standard error is a terminal and `NO_COLOR` is not set), `--ascii`, `--width <n>` (at least 40, since a frame's row numbers and a few columns need that much; the default stays 118), `-q`/`--quiet` and `-v`/`--verbose`. The word after `eval` is a statement and is never read as an option, so `zeff eval "-x"` reaches the parser. An option of a later release (`--frozen`, `--install`, `--memory`, `--threads`, `--fresh`, `--replay`, `--deny-warnings`, `--no-external`, `--refresh`, `--offline`, `-y`) is refused by name with "not available in this release yet", as the later commands are; an unknown option is a usage error.

**What each does.** `--width` is threaded from the command line through `RunOptions` to the interpreter and the display interface (`show_width`), where frames and tables break into blocks of columns; nothing else wraps. `--ascii` is a filter on both output streams in the command-line crate, applied to whole characters even when a write splits one: `·` becomes `|`, `×` becomes `x`, `…` becomes `...`, `→` becomes `->` and `—` becomes `-`; the engine never knows. Colour is likewise the command line's: the word before the first colon of an `error`, `warning` or `note` line is painted bold red, yellow or cyan with the usual escape codes, and nothing else, so the text is identical with colour stripped. `--quiet` hides notes only: `note:` lines under results and note-severity diagnostics of `zeff check`; warnings and errors always show. `--verbose` adds, after a run, "ran <script>: N statements in M ms", and to `zeff version` the target and the build kind (source build; official builds arrive with the launcher at 0.9.0).

**The scratch project.** `~/.zeff/scratch/` under `ZEFF_HOME` (the environment variable, else `HOME`, or `USERPROFILE` on Windows, plus `.zeff`), made on first use with the layout of `zeff new`. It belongs to the engine: when its `zeff.toml` pins another version or cannot be read, the file is written afresh rather than refused with Z0710, since the scratch project holds no analysis of record. Without a home folder, `eval` and the console say to set `ZEFF_HOME`. `zeff eval "<statement>"` runs the statement alone as a one-statement script named `eval` in the scratch project and prints what it prints; it does not touch the console's session, so a calculator use never grows a session, and it always runs in the scratch project, as section 2.1 says, even inside a project.

**The console.** `zeff repl` runs in the project around the current folder, or in the scratch project outside one. The session is `zeff_engine::session::Session`, a list of statement texts, saved as `.zeff/session.zeff` after every successful statement and read back when the console opens ("resumed N statements"; a file that no longer parses is set aside as `.zeff/session.previous.zeff` and the console starts afresh). Each statement typed is appended and the whole session re-run from the file (no result cache before 0.11.0); only the new statement's output is printed; a statement that fails for any reason is reported and dropped again, so the session always replays. A line that begins with `.` adds a step to the statement before it (that statement is taken back and re-run with the step appended, so a chain built line by line is one statement in the session script); a line that leaves a bracket open or ends with an operator continues on the next line, and an empty line ends an unfinished statement with its error. A comment alone is neither run nor kept. Prompts (`zeff> `, `  ... `) go to standard error and only when standard input is a terminal, so a piped session writes only its results to standard output, as Python's console does. `:undo` drops the last statement; `:vars` lists the bindings with their types from the checker, one line per name with the type of its latest `let`; `:save <path>` writes the session to a new file of the project (or to one it wrote in this session, never over another file), and outside a project `:save <name>` creates the project `<name>` in the current folder with the session as `scripts/main.zeff`; `:load <path>` runs a script's statements into the session as if typed (inside a project under the path rules; outside, relative to the current folder); `:help` alone lists these, `:help <name>` prints a help page or an explained code; `:quit`, `:q`, `:exit` and the end of the input leave. `zeff repl <script>` loads the script first. The session file is already in the `.gitignore` of `zeff new`.

**The specification corrected.** Section 2.1 said a second `let m` in the console is refused; the Language Reference (3.1) says a later `let` shadows, and the session is a script, so the Engine Specification now says so (docs/spec_changes.md).

**Tests.** Options from anywhere on the line and their refusals (unit); the ASCII filter across a split character and the colouring (unit); through the binary: `--width 60 --ascii` on a wide frame (snapshot of the blocks), the width's minimum, colour on and off and its bad value, quiet hiding only the note, verbose, `--project` from the parent folder and a wrong folder, a later option and an unknown one; `eval` printing 4 outside a project, an error with its position, a stale scratch pin repinned, the usage errors; the console inside a project (shadowing, `:vars`, a failed statement dropped, a two-line statement, a chain continued with `.describe()`, `:undo`, `:save` new, again and over an existing script, `:load`, `:help`, an unknown command, the session file, resuming, `zeff repl <script>`) and outside one (the scratch project, `:save` creating a project that then runs); the scratch project made once and repinned, and the session split, saved, resumed or set aside (engine unit tests).

## 19 October 2026: Maths, part 1, and scalar functions on columns

**Scalar functions on columns.** Section 3.7 says every built-in scalar function of `core` applies row by row when given a column and returns a column. The bodies are written for one row; the lifting is one place, `zeff_core::lift::call_rowwise`, used by the interpreter when the checker has marked a call as lifted. The checker marks it when the function is a non-method function of `core`, a parameter's declared type is a scalar type (Bool, Int, Float, Str, Date, DateTime, or a union of these) and the argument is a column whose row type that parameter accepts; the call's type is then `Column<T>` of the declared result. `print`, whose parameter is `Any`, is never lifted. At run time the body is called once per row, a scalar beside a column standing for its value in every row, the columns must share a length (Z0217), a warning raised in several rows is said once with the count ("sqrt of a negative number gave NA in 12 rows"), and an error in a row names the row. Warning wordings therefore name the cause and never the value, so that rows of one cause count under one line. The result column's type is that of the values present, or the declared result type when every row is `NA`. This is a row-by-row call, not a vectorised kernel: a few hundred nanoseconds a row, which is fine for everyday data and can be replaced function by function if a profile ever asks.

**Result types.** A declared result type `Number` means "Int when every number given is an Int, Float otherwise" (section 3.7): `abs`, `min`, `max`, `div` and `mod` use it, so `div(10, 3) * 3` stays in Int arithmetic. `sign` returns an Int (the catalogue says "-1, 0 or 1"; R returns a double), `is_finite` a Bool, the rest a Float. Further positional arguments (`min(a, b, ...)`) are now type-checked like parameters (Z0401), which they were not before.

## 19 October 2026: The remaining options of `import` for delimited text

**Choice.** `quote:`, `decimal:`, `thousands:` and `encoding:` complete the options of section 6.1 for delimited text. `quote:` is one ASCII character (`"` by default) and `quote: ""` turns quoting off, so that a quotation mark is an ordinary character; the record splitter and the delimiter detection take the quote character as a parameter. `decimal:` and `thousands:` are one character each, held in a `NumberFormat` that every number parser of the reader takes (type guessing, the cells, the `na_values:` codes), so that the whole file is read under one rule: a value is a number when, after the grouping separators are removed, it is a number written with `.`; a grouping separator must stand between groups of exactly three digits after a first group of one to three, and only before the decimal mark, so `1,23` and `12,3456` are text under `thousands: ","` rather than numbers read wrongly; with a decimal comma a `.` makes the value text; the words `Inf` and `NaN` are numbers in every format. ## 19 October 2026: Frame verbs, part 1, and names inside a frame method

**Names inside a frame method.** `where(hours > 36)` needs a bare name in a frame method's argument to mean a column of the receiver, which the specification orders before a script binding (section 3.7, "Name lookup") and which the engine did not have. The checker now marks a call as a frame method when its receiver parameter is a `Frame`, and checks every argument whose parameter type takes a column (`Column<Bool>`, `Column`, a union with one; `Var`, `Vars`, words and plain scalars keep their own rules) with the receiver's columns in scope: a bare name there lowers to a new IR node, a frame name holding the name and the binding of that name if one is in scope. Since the frame's columns are not known before the run (the schema cache is 0.3.0), the node is resolved by the interpreter, which keeps a stack of the frames whose methods are being called: the receiver is evaluated first, as section 3.7's argument order already had it, and pushed while the other arguments are evaluated. The column wins; the binding is used when the frame has no such column; both at once is the column with a warning, the provisional W0102, added to open decision #46 (the specification asks for the warning and gives it no code); neither is Z0101 with the frame's variables suggested. A frame name with a binding in scope is typed as unknown, so that `where(hours > w.mean(hours))` can still call a method on the binding; without one it is a column of unknown type. The interpreter also records which columns a call's arguments named, in the order first used, and hands them to the body (`columns_used` on the call context, beside the script's text so that a body may quote an argument as written), which is how `where`'s note names the variable whose `NA` dropped rows: the first used column that has any `NA`, as `wages.where(is_missing(exper))` in the specification's own example. A `Column<Bool>` parameter given a single Bool or `NA` is refused by the checker as Z0203, in the words section 5.6 uses, rather than as a generic Z0401.

**Variable ranges.** `x1..x9` where variables are expected (a parameter of type `Vars`, alone or inside a list) is kept as one entry `x1..x9` of the variable list and expanded against the frame by the data package's `resolve_vars`, which also drops a repeated name and refuses a range that runs backwards (Z0401, listing the frame's variables in order); the shared helper is there for every verb and reducer that takes variables.

**The verbs.** `head` and `tail` slice (a count below zero or `NA` is Z0401); `where` takes a Bool column of the frame's length (another type is Z0203, another length Z0217), keeps the true rows, counts the `NA` rows into the note with the statement that lists them, and says when nothing is kept; `select`, `drop` and `rename` share the parent's columns, keeping every column's metadata and the frame's, and `rename` refuses a name another variable has (Z0401). A derived frame has no name until a `let` gives it one, so it prints as `frame · …` and its messages say "the frame". In the column kernel, `Column::take` gathers rows through `arrow-select` (60.0.0, Apache-2.0, the arrow family already recorded), which handles every storage, the opaque kinds included, and `Table` gained `tail`, `take_rows`, `select`, `without` and `rename`. The selection vector of section 6 (sharing the parent's buffers until a later step reads a column) is not built yet: `where` gathers at once, which is correct and simple; the lazy form arrives with the result cache.

## 19 October 2026: Frame verbs, part 2: `add`, `update` and `sort`

**Definitions that see earlier ones.** Section 3.7 says the definitions of `add` and `update` are evaluated left to right and a later one may use an earlier one. The interpreter's receiver entry now holds two frames: the frame as given, which the call's options see, and the frame extended with every definition evaluated so far, which the definitions after it see; a flag says which is being evaluated. The first attempt extended one frame for everything, and `update(hours = 38, where: is_missing(hours))` then saw no missing hours in its condition; the help example caught it. A scalar definition (`year = 2026`) is broadcast to a column of the frame's length for this purpose and for the result (`zeff_core::lift::broadcast`, shared with the verbs).

**`add`.** Each definition becomes a column of the frame's length: a column of that length (another length is Z0217), or a scalar in every row; `NA` alone has no type (Z0219, with the hint to build it from a variable); a list or a record is refused (Z0401). ## 19 October 2026: The reducers, `by:` and `weights:`

**One engine for every statistic.** `reducers.rs` now computes every descriptive statistic (`mean`, `sd`, `variance`, `median`, `quantile`, `min`, `max`, `sum`, and the columns of `summary`) through one path: the frame and the variable, the weights of `weights:` with `weight_type:` (the kernel's `Weights` of step 6, with its rules of section 4.1: an `NA` weight drops its row with a warning, a zero weight leaves it out with a note, a negative, infinite or, under frequency weights, fractional weight is an error listing the rows), the groups of `by:` (the kernel's `Groups`, in key order with `NA` last), and a `Sample` per group holding the values that count, their weights and the number of `NA` values skipped. Without `by:` the result is a value; with it a table titled `mean · wage by region`, the keys in the first columns and the statistic to three decimals (section 3.8's rule for tables), in the layout section 10.2 shows for `summary`. The warnings are counted across groups and said once. `summary` and `describe` take `by:` the same way, `describe` with one block of rows per group.

**The weighted formulas (the owner's decision of question 1).** In the numeric kernel (`zeff_numeric::order`): `weighted_mean` is Σwx / Σw for every weight type; `weighted_variance` under frequency weights replicates rows (divisor Σw − 1) and under analytic and sampling weights scales the weights to sum to n with divisor n − 1, as Stata's `summarize [aweight]`; `weighted_sum` is Σwx under frequency and sampling weights and n · Σwx / Σw under analytic weights; `weighted_quantile` and the weighted median take the smallest value whose cumulative weight reaches p of the total, the type-1 quantile of the replicated sample under frequency weights; `n` in `summary` is the weight sum under frequency weights and the row count otherwise; `min` and `max` ignore the weights beyond leaving out the rows that do not count. The R script `descriptive.R` now writes these statistics on the large wages file with `educ` as the weights (base R: `weighted.mean` and the formulas written out), and the kernel is held to them within 1e-12; without weights, `sd` and `variance` keep the kernel's scaled two-pass algorithms, since a square root of a weighted variance would underflow for values near 1e-300 (the test on the magnitudes dataset caught the first version).

**The nine quantile definitions.** `zeff_numeric::order::quantile` is R's `quantile.default` written out, its fuzz against rounding in the index included, so the nine types agree with R to the bit on every dataset of the reference at nine probabilities; the small-sample unit test records that types 3 and 4 differ from the others at the median of 1, 2, 3, 4, 10 (2 and 2.5 where the rest give 3). `type:` outside 1 to 9, and `p:` outside [0, 1] or not a number, are Z0401 (the code Z0413 of section 4 is for the probabilities given to distributions, which arrive at 0.3.0); `p:` missing is Z0406.

**Reducers inside `add` and `update`.** Section 6 makes every statistic a reducer inside a definition: `add(dev = lwage - mean(lwage), by: firm)`. Three pieces: (1) a bare call to a frame method inside a frame method's definition is an *implicit-receiver* call, which the interpreter gives the enclosing frame as its receiver (the group under `by:`); when a name has a row-wise home in `core` and a reducer home in `data` (`min`, `max`), the reducer is chosen inside a definition when the arguments fit it (one variable, where the row-wise function needs two values), section 8.1's rule 6 read at the call; (2) under `by:`, a definition is evaluated once per group on the group's rows (the receiver's view) and the results are put back in row order, a scalar filling the group's rows, a column of the group's length placed row by row, another length Z0217, kinds that do not join across groups Z0214; so `n()` and `n_distinct(x)` count within the group with no special case; (3) the options of a frame method that takes definitions are evaluated before its definitions whatever the written order, since `by:` shapes them, a reading of section 3.7's "positional then named" that puts the named options first. The messages of a definition evaluated per group are said once per distinct wording. `n()` outside a frame method is Z0401 pointing to `n_rows`; `n_distinct` counts by identity, `NA` one value, as the catalogue says. The call context carries the enclosing frame as the call sees it, for `n()`.

## 19 October 2026: The special-function kernel

**Choice.** `zeff_numeric::special` holds the functions the distributions need, in pure Rust on every target: `log_gamma`, `gamma`, `erf` and `erfc` from the `libm` crate like the elementary functions (musl's ports, a unit or two in the last place; `gamma` returns the exact factorial at the integers 1 to 171, where libm's value may be a unit off); `factorial` from a table of the 171 doubles nearest the exact values, written once by Python's exact integers; `choose` exactly while the integers fit in 128 bits, then one rounding per step, and `Inf` once `k` exceeds 600 (the result then exceeds the largest double whatever `n`); `log_beta` through the Stirling form, so that large arguments lose no digits to cancellation; the normal tails from `erfc` on each side, and the normal quantile by Halley steps on `erfc` from the Abramowitz and Stegun start, exact at one half; the regularised incomplete gamma function by its series below a + 1 and its continued fraction above (modified Lentz), the regularised incomplete beta function by its continued fraction on whichever side converges, each returning both tails with the small one computed directly (section 13: tails are never one minus the other side); and the inverses by safeguarded Newton steps with a bracket, on the smaller tail, from the Wilson–Hilferty and normal starts.

**The prefix terms.** The exponent of each prefix, a ln x − x − ln Γ(a) and a ln x + b ln(1 − x) − ln B(a, b), is the place where a large parameter loses digits: written naively it subtracts numbers of size a ln a. It is computed instead from the Stirling remainder S(x) = ln Γ(x) − [(x − ½) ln x − x + ln √(2π)] (the Bernoulli series from x = 10, the difference itself below) and the deviation from the mean: for the gamma function a·(log1p(d) − d) with d = (x − a)/a by its own series near zero, and for the beta function a log1p(d/a) + b log1p(−d/b) with one rounded deviation d = x(a + b) − a, so that the two terms' first-order rounding errors cancel (the derivative of their sum with respect to d vanishes at the mean). Far from the mean, where log1p would meet an argument at −1, the plain logarithm of the ratio serves, the result then being deep in a tail where the exponent's size bounds the error. Three attempts were needed to find the form that keeps both tails of the beta function to twelve digits at a = 500,000, and each wrong turn was caught by the exact reference, not by R, whose values at those points carry errors of the same order.

**The references.** `tests/reference/special.py` computes every value in Python's `decimal` module at 70 digits and rounds once: the gamma function by the Stirling series with exact Bernoulli numbers after a shift to 50, the error functions by the Maclaurin series up to 5 and the continued fraction beyond, the incomplete functions by the same series and continued fractions at 85 digits, the inverses by bisection (in log space for a lower tail, which may lie at 1e-100) followed by Newton steps with the bracket kept. `mpmath`, which the checklist named, is not in the standard library and the rules allow no installer for it; `decimal` suffices and runs in eleven seconds. `tests/reference/r/special.R` writes R's values on the same cases (`special_cases.csv`, exact hexadecimal floats) and CI compares them within 1e-12 (`check_r.py special`), since R's `pgamma` and `pbeta` differ between platforms in their far tails at that order.

**Tolerances found.** Against the exact reference: `log_gamma`, `gamma`, `log_beta` and the exact binomial coefficients to 1e-14; `beta`, `erf`, `erfc` and the normal tails to 5e-13 (a value through an exponential of a logarithm near −60 rounds by 1e-14; `erfc` at 20 and beyond carries 1e-13); the incomplete functions and their inverses to 1e-12, widened in a deep tail in proportion to the exponent's size (a probability of 1e-235 is exp(−541), and 1e-16 of 541 is 5e-14), and to 1e-10 for a parameter above 100,000, where the continued fraction's stopping rule cannot see below a unit in the last place and leaves an error of about 2e-11: the single departure from the class tolerance, recorded as a known issue of 0.3.0 and to be closed by the asymptotic expansions of Temme (as TOMS 708 does) in a later step or release; a t distribution with a million degrees of freedom is the case that meets it. Eight conformance series (`special/*`) hold the bits on the four targets.

**Tests.** `reference_special.rs` (the exact reference, 599 values), the special section of `reference_r.rs` (R), three property tests (the gamma recurrence; both tails are probabilities that sum to one, are monotone and mirror between I_x(a, b) and 1 − I_{1−x}(b, a); every inverse round-trips its function to 1e-11), and the unit tests of the domain edges and the deep tails.

**Reason.** Engine and Project Specification, sections 8.3 point 3 (one pure-Rust implementation, fixed order) and 13 (tails computed directly; the distribution class); testing handbook, section 1.1; the checklist's step 2.

## 19 October 2026: Philox random streams and the run's seed

**The generator.** `zeff_numeric::random::philox4x32_10` is Philox4x32-10 exactly as the Random123 library defines it (the multipliers D2511F53 and CD9E8D57, the Weyl constants 9E3779B9 and BB67AE85, the key bumped between rounds), and its unit test holds the three published known-answer vectors (all zeros, all ones, and the π digits), so a draw means the same on every machine and in any other implementation of the same function. ## 19 October 2026: The t, chi-square, F, gamma and beta distributions

**Choice.** `dist.t(df:)`, `dist.chi2(df:)`, `dist.f(df1:, df2:)`, `dist.gamma(shape:, rate: 1)` and `dist.beta(a:, b:)`, each on the kernel's incomplete functions: the chi-square and gamma distribution functions are P(α, λx) with Q computed directly, the F's is I_w(d₁/2, d₂/2) at w = d₁x/(d₁x + d₂), the beta's is I_x(a, b), and the t's is half of I_x(ν/2, ½) at x = ν/(ν + t²) on the side of t. The densities use the kernel's `gamma_density` and `beta_density` (the F's as the beta density at w times dw/dx), whose prefixes keep their digits for large parameters, and the t's density is written in logarithms with the beta function. Every quantile inverts on the smaller tail, the F's and the t's solving for 1 − w through the mirrored inverse when w would be near one. Degrees of freedom and shapes may be fractional, as in R, but must be finite: `dist.t(df: Inf)` is refused (Z0413) rather than read as the normal, since the specification gives `df:` the domain "positive" and nothing more. Above 400,000 degrees of freedom the t distribution uses the normal approximation R itself uses in `pt` (z = t(1 − 1/4ν)/√(1 + t²/2ν)), so the engine and the reference agree there exactly and the continued fraction's loss of digits at such parameters (the known issue of step 2) does not reach the t distribution; its quantile there is found by Newton steps from the normal quantile.

**Deep tails.** Three limits of double precision met on the way, each handled in logarithms. Past |t| = 1e150 the ratio ν/(ν + t²) lies below the smallest Float, so the t tail is its leading term, ½ x^(ν/2) / ((ν/2) B(ν/2, ½)) with ln x = ln ν − 2 ln |t| (a Cauchy tail at −1e300 is 3.18e-301, as R gives), and the deep-tail quantile inverts the same term; the normal approximation above 400,000 degrees of freedom is written as (1 − c) sign(t) / √(1/t² + 2c) so that a huge t does not become a ratio of infinities; and the kernel's inverse incomplete functions return the end of the interval outright when a tail's leading term lies below the smallest Float, instead of bisecting towards it for two hundred steps. R's `qbeta`, and so its `qf`, loses digits deep in a tail (`qf(1e-20, 3, 20)` returns a value whose `pf` is 1.02e-20, two per cent off, and at 1e-300 it returns 0 where the quantile is 7.9e-201); the test therefore holds a quantile that differs from R's to the round trip through the distribution function instead, within a few parts in a million of the printed six digits, and the engine's values pass it where R's do not.

**Tests.** R's `distributions.json` now holds fifteen more parameter sets (t at 1, 3, 24 and 1e6 degrees of freedom; chi-square at 1, 5 and 100; F at (3, 20), (1, 1) and (100, 1000); gamma at (0.5, 1), (2, 3) and (100, 0.1); beta at (0.5, 0.5), (2, 3) and (100, 100)), each on the grid of x from −1e300 to 1e6 and of p from 1e-300 to 1 − 1e-10, and every printed value agrees at six digits; the edges of each support (densities at zero infinite, one or zero as the shape decides; the t's median exactly zero and its quantile at zero −Inf); the refusals (Z0413 for a zero or negative parameter, a missing one Z0406); the stochastic class on 100,000 draws of each of the nine families; eight more parameter sets in the conformance series.

**Reason.** Language Reference, section 4; Engine and Project Specification, section 13; the catalogue rows 181 to 183, 189 and 190; the checklist's step 8.

## 19 October 2026: The binomial, Poisson and negative binomial distributions

**Choice.** The three discrete families take whole numbers only: `pdf` at a value that is not a whole number is 0 (R's `dbinom` gives 0 with a warning; Zeff gives 0 without one, since the value is a legitimate point of the real line where the mass is zero), `cdf` counts up to the whole number below its argument, and `draw` gives a `Column<Int>` as the owner decided. The probabilities are computed in Loader's saddle-point form, exp(S(n) − S(k) − S(n − k) − D) / √(2πk(n − k)/n), with the kernel's Stirling remainders and a new kernel function `deviance(x, m)` = x ln(x/m) + m − x evaluated by its series near x = m, so that the probability of a thousand successes in a million trials is right to every digit where the logarithm of the binomial coefficient would lose nine; the Poisson uses the same form with one term, and the negative binomial is size/(size + k) times the binomial probability of `size` successes in k + size trials, which holds for a fractional size. The distribution functions are the incomplete beta and gamma functions with both tails direct (binomial I_{1−p}(n − k, k + 1), Poisson Q(k + 1, λ), negative binomial I_p(size, k + 1)). A discrete quantile is the smallest k with F(k) ≥ p, found from the normal approximation by widening a bracket and halving it, a few dozen evaluations of F however far the quantile lies; `quantile(1)` is `n` for the binomial and `Inf` for the others, as in R.

**Whole numbers with R's tolerance.** A value within one part in ten million (relative) of a whole number counts as that whole number in `pdf`, and `cdf` floors with the same tolerance, as R's `dbinom` and `pbinom` do, so that floating-point noise such as 2.9999999999 on a computed count does not turn a probability into zero; a negative value is below the support before any rounding, as in R, so `pdf(-1e-10)` is 0 where `pdf(1e-10)` is the mass at zero. The first version had neither rule and the R comparison caught both.

**Two parameterisations.** `dist.negbinomial` takes `size:` with `p:` or `mu:` with `size:`; both together are Z0410 (the provisional code of open decision #46 for options that exclude each other) and neither is Z0406; the value keeps the form it was given and prints it, converting with p = size/(size + mu) when it computes. The catalogue writes the two forms joined by ` or `, and the registry's reading of a usage now takes the union of the parameters of every form, which the help contract foresaw for `t_test`.

**Tests.** R's file holds nine more parameter sets (binomial at (10, 0.3), (1000, 0.5) and (1e6, 1e-3); Poisson at 2, 0.01 and 1000; negative binomial at (3, 0.4), (mu 4.5, size 3) and (0.5, 0.1)), every printed value agreeing at six digits; the edges (fractional and out-of-range arguments, the quantiles at 0 and 1, the point mass at `p: 1`, the Int draws); the refusals (a fractional `n` Z0401, a probability outside [0, 1] Z0413, both or neither parameterisation); the stochastic class on 100,000 draws of the three families, with the Kolmogorov–Smirnov distance taken at the distinct values, as a discrete distribution requires; three more parameter sets in the conformance series.

**Reason.** Language Reference, section 4; Engine and Project Specification, section 13; the owner's decision on question 3; the catalogue rows 184 to 186; the checklist's step 9.

## 19 October 2026: `dist.truncated` and `dist.mixture`

**Truncation.** `dist.truncated(d, lower: -Inf, upper: Inf)` builds the `Truncated` shape of the value: with Z = P(lower ≤ X ≤ upper), the density is f/Z on the interval, the distribution function (F(x) − F(lower⁻))/Z and its upper tail (S(x) − S(upper))/Z, each from the inner tail on the same side so that a far tail keeps its digits, and the quantile the inner quantile at F(lower⁻) + pZ held inside the interval. For a discrete distribution the interval is closed at both ends (the mass at `lower:` is kept; the `truncdist` package drops it, its interval being open below), the reading a statistician gives "truncated to [a, b]". A bound not above the other, or an interval holding no probability, is Z0413. Near the inner centre the subtraction keeps about eleven digits, which the help page says.

**Mixtures.** `dist.mixture(parts, probs:)` builds the `Mixture` shape: density and both tails as weighted sums, the quantile as the smallest x with the mixed distribution function at or above p by halving a bracket set by the components' quantiles (landing on a whole number when every component is discrete), and a draw spending two uniforms of the stream, one to choose the component and one to invert through it, exactly as section 8.3 fixes. The probabilities must be 0 or more and sum to one within 1e-9 (Z0413), one per component (Z0401), `probs:` required (Z0406); they are normalised by their sum. `families::draw` now takes the stream rather than one uniform, so that a mixture can draw twice; its callers in the engine, the conformance report and the tests follow.

**The reference without `truncdist`.** The checklist named R's `truncdist` package as the reference for truncation. It is an R package and the rules allow no installer for one (R itself came through Homebrew), so `distributions.R` writes the truncated and mixed functions from base R's own: the formulas above, which are what `truncdist` computes, and `uniroot` for the mixture's quantile. The comparison allows a composite one part in a hundred thousand, since both sides subtract near-equal probabilities; a discrete quantile that differs from R's is held to the smallest-k property (F(k) ≥ p and F(k − 1) < p), where the R formula `qpois(F(a − 1) + pZ)` falls below the interval when pZ is lost in the addition.

**A correction found on the way.** The t distribution near its centre: the ratio ν/(ν + t²) rounds towards one and loses the digits of F(t) − ½, so for |t| < √ν the complement y = t²/(ν + t²) is used with I_x(ν/2, ½) = 1 − I_y(½, ν/2); the truncated t on [0, ∞) at 1e-10 showed it (0 where 7.6e-11 is right). The catalogue's usage of `dist.mixture` named no first parameter (`[d1, d2, ...]`, an example literal); corrected to `parts` and logged in `docs/spec_changes.md`.

**Two kernel properties made honest.** The full run caught two random cases of the kernel's properties. A beta quantile in an upper tail with a small second shape (a = 39, b = 0.1, p = 1e-12) has no double below one with so small a tail: the inverse now returns one when the leading term (p b B(a, b))^(1/b) lies below half a unit in the last place of one, and the round-trip property accepts the returned double when its two neighbours' tails straddle p, the honest statement where the function is too steep for the grid of doubles to hold a quantile whose tail returns p to eleven digits. The symmetry property I_x(a, b) = 1 − I_{1−x}(b, a) now allows 1e-9 instead of 1e-12: 1 − x is rounded, and a far tail moves by about a/x units in the last place when x does (a up to 2,000 and x near 0.005 in the case found).

**Tests.** The R comparison extended by four composites (a truncated normal on [−1, 2], a t with five degrees of freedom on [0, ∞), a Poisson on [1, 6], a mixture of two normals); a snapshot of their printing, edges and draws; the refusals; the stochastic class on 100,000 draws of the truncated normal and of the mixture against their exact moments; both in the conformance series. The two catalogue rows are `implemented`; the twelve families, the two constructions and the four methods of the release are complete.

**Reason.** The catalogue rows 425 and 426; Engine and Project Specification, sections 8.3 point 3 and 13; the checklist's step 10.

## 20 October 2026: `seed`

**Choice.** `seed(n: Int)` in `core`'s program functions sets the run's seed on the `Randomness` of step 4 and returns nothing. ## 23 October 2026: The `zeff-kernels` crate

**Choice.** `kernel/zeff-kernels` is the linear-algebra module of section 8.1, rule 8: pure Rust, `unsafe` denied, no dependency. It holds a dense column-major `Matrix`; the reductions in the shape of open decision #47 (`reduce`: `LANES` independent accumulators, element i going to accumulator i mod `LANES`, each with Knuth's two-sum error term, the accumulators combined in lane order at the end, and the rotation carried across slices so that a sequence gives the same bits however it is cut; `sum`, `dot`, `sum_of_squares`, `norm`); matrix products whose every entry is such a dot product (`product`); Householder QR with LAPACK's reflector convention (`qr::r_factor`); the tall-skinny QR (`qr::TallSkinnyQr`), which re-cuts the rows it is given into blocks of `BLOCK_ROWS` = 65,536, factorises each block on its own and folds the block's R into the running one in block order, the shape of #48, so that a parallel version computing the block factors on several threads gives the same bits; the limited column pivoting of R's `dqrdc2` (`qr::pivoted_qr`: the columns factorised in order, a column whose remaining norm is below the tolerance times its own original norm moved to the end and left out, a zero norm counting as one so that a zero column is left out too, and columns beyond the pivot candidates transformed but never pivoted, so that the outcome rides along as the last column of `[X y]` and the residual sum of squares is the sum of squares of its tail); `qr::least_squares` on those, returning the kept R factor as well, from which (XᵀX)⁻¹ and the leverages follow; triangular solves and the triangular inverse (`triangular`); Cholesky with the first pivot that is not positive reported (`cholesky`); and the singular values by one-sided Jacobi rotations in a fixed sweep order, with the 2-norm condition number from them (`svd`). Inputs are finite and below about 1e150 in magnitude, which the model layer guarantees.

**Why 65,536 rows a block.** Section 8.3, point 10 allows up to a million; a block of a hundred columns then weighs 800 MB, where 65,536 rows weigh 52 MB, and the fold of a 2k × k stack per block costs nothing beside the block's own factorisation. The constant is part of the numerical definition of a fit and changes only with a release note.

**Why no intrinsics.** Section 8.3, point 3 names explicit 128-bit SIMD; what the contract needs is that the bits do not depend on the width, and the lane shape gives exactly that: the compiler may vectorise the lane loop or not, the operations and their order are the same. Intrinsics would need `unsafe` in the kernel; they are an optimisation for a later release if the benchmarks of #52 ask for one, and would change no bit. Two things the measurement of this step taught about the shape in Rust: the accumulators are copied to local arrays for the chunk loop, since through `&mut self` the compiler keeps them in memory; and the product loop takes the sum loop's form (the products of a chunk into an array, then one pass over the lanes), because a loop that zips the two chunks and enumerates the lanes compiles to code five times slower with the same arithmetic.

**Why recomputed norms in the pivoting.** `dqrdc2` downdates the column norms as it goes and recomputes one when the downdate loses accuracy; the kernel recomputes every remaining norm from the transformed column, which on the k × k factor the fit hands it costs nothing beside the QR of the rows and is deterministic by construction. The decisions agree with R's on every case of the reference; the order among the columns left out is that of the moves and means nothing.

**Tests.** 25 unit tests of exact small cases in the modules, so that a mutant dies in the crate's own suite in seconds (the lesson of the 0.3.0 close); `tests/properties.rs` (a sum cut into slices of any sizes gives the same bits; integer sums and dot products are exact; RᵀR is XᵀX within rounding; the blocked QR equals the block factors folded in order at any block size and any way of handing over the rows; a column scaled by a power of two scales its coefficient exactly and changes no other bit, since every operation of the factorisation commutes with such a scaling; a triangular solve inverts its product; the Cholesky factor reproduces its matrix; the singular values carry the Frobenius norm); `tests/reference_exact.rs` against `tests/reference/kernels.py`, which computes twelve least-squares cases in exact rational arithmetic with Python's `fractions` on the binary values of the inputs (columns at 1e7, 1e9 and 1e12, an exact duplicate, a near-collinear column dropped at 1e-9 and kept at 1e-5, a zero column, a wide matrix, an exact fit; the collinearity rule applied exactly), a triangular system with its inverse, a positive-definite system, and sums whose compensation matters; `tests/reference_r.rs` against `tests/reference/r/kernels.R` (R 4.6.0's `qr` with its limited pivoting and `qr.coef`, `qr.resid` and the leverages from `qr.Q`, the singular values, `backsolve`, `chol` and the solve through the factor; the same inputs as hexadecimal floats, read exactly). The tolerances scale with the condition number of the kept columns once each is scaled to unit norm, 1e-14 times it with a floor of 1e-12: on the case whose condition number is 3.3e5 the kernel and R each lie about 7e-11 from the exact solution, on opposite sides, which is what the condition allows. Six `kernels/*` series in the conformance report (the reductions, a 1,000 × 6 least-squares fit through four folded blocks with a duplicate column left out, its R factor, the inverse, the Cholesky factor of the kept Gram matrix, the singular values and the condition number) hold the bits on the four targets. The reference job of CI re-runs both scripts and compares R's file within 1e-12.

**Two things learnt about R.** `solve` (LU with partial pivoting) loses four digits on the positive-definite case, a matrix with a diagonal entry of 1e12 beside entries of order one, where the solve through the Cholesky factor keeps ten, so the script solves through `chol`, as the kernel does. And `qr` on an n × k matrix with k > n stops at row n and leaves the surplus columns where they are, while the kernel, which pivots the k × k factor, moves them to the end; the columns kept are the same.

**Reason.** Engine and Project Specification, sections 8.1 (rule 8), 8.3 (points 3 and 10) and 13; Language Reference, section 7.2 ("Collinearity"); open decisions #47 and #48 as the owner took them; the checklist's step 2.

## 23 October 2026: The reduction shape measured, and N = 16 (open decision #47)

**The measurement.** `cargo bench -p zeff-kernels --bench reduction` (criterion 0.8.2, release profile): one sum and one dot product over ten million doubles in [−0.5, 0.5), the scalar Neumaier sum shipped in `zeff-numeric` since 0.1.0 against the two-sum lane shape at 2, 4, 8, 16 and 32 lanes, with a plain uncompensated loop as the floor. On the owner's machine (Apple M2 Pro, ARM64, 128-bit NEON), the mean of twenty samples:

| Shape | Sum | Dot product |
| --- | --- | --- |
| Plain loop, no compensation | 8.61 ms | 8.59 ms |
| Neumaier, scalar (`zeff-numeric`; the dot as products into a vector, then its sum) | 10.81 ms | 13.40 ms |
| Two-sum, 2 lanes | 5.01 ms | 6.76 ms |
| Two-sum, 4 lanes | 3.08 ms | 6.14 ms |
| Two-sum, 8 lanes | 2.69 ms | 6.08 ms |
| Two-sum, 16 lanes | 2.56 ms | 3.11 ms |
| Two-sum, 32 lanes | 2.63 ms | 3.53 ms |

A plain loop is a chain of dependent additions, so it is no faster than the compensated scalar sum; the lanes break the chain. The dot product's dip at 4 and 8 lanes is a code-generation accident of those widths (the same arithmetic in a throwaway probe ran at 3.8 ms with 8 lanes), not a property of the shape.

**Choice.** `LANES` = 16: the fastest shape for both reductions on this machine, 4.2 times the speed of the scalar Neumaier sum and 4.3 times that of the scalar dot product. The figure is now part of the numerical definition of every reduction of `zeff-kernels` and changes only with a release note. The same benchmark on the x86-64 runner (GitHub-hosted, a baseline SSE2 build, as the official x86-64 builds are; run 39852353049) gave, for the sum, 9.45 ms plain, 15.10 ms scalar Neumaier, 9.55, 6.01, 5.69, 6.97 and 5.97 ms at 2, 4, 8, 16 and 32 lanes, and for the dot product 9.58 ms plain, 24.84 ms scalar, 11.97, 8.72, 7.64, 6.20 and 6.53 ms: there 8 lanes is a fifth faster than 16 on the sum and 16 is the fastest on the dot product, four times the scalar. Sixteen is the best shape on the owner's machine for both reductions and the best or within a fifth of the best on the runner, so it stands.

**Consequence.** The owner's decision of 23 October 2026 moves the reducers of 0.1.0 to 0.3.0 to the shape at this release when the gain is a fifth or more; at fourfold it is, so the checklist gains step 2b, in which `zeff-numeric`'s sums move to `zeff_kernels::reduce` one routine at a time, with the changed last digits of the published conformance cases regenerated deliberately and listed for the release notes.

**Reason.** Open decision #47 as recommended and taken ("N fixed by that measurement and recorded once"); section 8.3, point 3; the checklist's step 2.

## 23 October 2026: The reducers of `zeff-numeric` on the reduction shape (step 2b)

**Choice.** Every sum over values in `zeff-numeric` is now the lane sum of `zeff-kernels` (a kernel crate may depend on a kernel crate): `sum` is `zeff_kernels::sum`; `mean` sums the values and then the deviations in that shape; the scaled two-pass variance behind `variance` and `sd` takes the sum of squares and the sum of the scaled deviations from it; `covariance` and `pearson` take the dot products and sums of squares of the centred series; the weighted mean, sum and variance already went through `sum` and moved with it, as did the weight totals of the column kernel and the `sum` statistic of `data`. The Neumaier accumulator is gone. Three loops stay sequential by nature and are not sums over rows: the running total of the weighted quantile (a prefix sum, where the order is the definition), the series and continued fractions of the special functions, and the small fixed sums over the components of a mixture distribution or the tie groups of Kendall's variance (exact integers in the latter case); the shape of #47 is for reductions over observations.

**The fallback.** The whole-slice functions of the kernel (`sum`, `dot`, `sum_of_squares`) keep the documented behaviour of the old `sum`: a result that is not finite is replaced by the plain left-to-right IEEE sum, which gives `Inf` for `Inf` alone, not-a-number for `Inf` with `-Inf`, and may still be finite where the lanes overflowed on the way (sixteen alternating values of ±1e308 sum to 0 in order and to not-a-number by lanes); the streaming accumulator, having no slice to return to, folds its lane sums plainly.

**What changed in the published results: nothing.** Every one of the 127 lines of the conformance report, the three sample projects' stored output, the exact and R references of 0.1.0 to 0.3.0 and every snapshot are unchanged by the move. That is what the arithmetic predicts: a compensated sum of some thousands of values is the correctly rounded exact sum except at rare boundaries (an independent check in exact rational arithmetic found the two orders equal, and both correctly rounded, in 200 of 200 series of 10,000 values), so two compensated orders agree to the bit. The release notes therefore list no changed digit for this step. A test in `zeff-numeric` holds each moved routine to the kernel's lane sums to the bit.

**The design.** `Design::build(ctx, frame, formula, extra)` takes a frame value, a formula value and the names of further model variables (weights, a cluster), and gives the column names, the rows used, the rows dropped for `NA` with a count by variable, the notes, and the design in row blocks of the kernels' size (`BLOCK_ROWS`, open decision #48), each block a matrix with the block's outcome; `matrix()` gathers the whole for tests. The contrast weights are R's `contr.treatment`, `contr.sum`, `contr.helmert` and `contr.poly`; the polynomial ones are computed by Gram–Schmidt with reorthogonalisation over the centred, scaled positions, in a fixed order of pure IEEE operations, with a positive leading coefficient so that the signs are R's. A category of one level adds no column, with a note, where R stops with an error. The indicator columns of `category(x, ...)` and `base(x, ...)` are named by `x`; a level holding `=`, `:` or `+` is quoted inside the name (section 7.2); a variable's term name is its name as text, without backticks, as `m.coef("x y")` will write it.

Text in the model is Z0401 pointing to `category`; a category as the outcome is Z0401 until `logistic`; a date is Z0304 naming 0.6.0; a missing variable is Z0101 with the frame's variables. A term calls the functions of `core` only (`log`, `category`, `base`, the lifted scalar functions), through the function table of `core` and the row-wise call of section 3.7; a reducer in a term is refused by the checker's ordinary rules, and a call to another package's function is Z0401 with the help to compute it with `add` first. ## 23 October 2026: The variance layer (step 11)

**The layer.** `results::variance` computes every kind of standard error from an estimator's scores and bread (Engine and Project Specification, section 8.3, point 2), by the rulings of the release: `classical` is σ²(XᵀX)⁻¹ with σ² the residual sum of squares over N − k; `robust` is HC1, N/(N − k) times the sandwich B(Σ sᵢsᵢᵀ)B of the scores sᵢ = xᵢeᵢ; `hc2` and `hc3` scale each row's score product by 1/(1 − hᵢ) and 1/(1 − hᵢ)²; `cluster:` is CR1, the scores summed within each cluster (a dependence structure: the row pairs within a cluster weigh 1 and the others 0), with Stata's adjustment G/(G − 1) · (N − 1)/(N − k); the t table uses N − k degrees of freedom, or G − 1 when clustered, as Stata's `regress` and reghdfe do and as `sandwich::vcovCL(type = "HC1")` reproduces. The meat is accumulated block by block from the estimator's scores, so no n × k matrix is held; a cluster's scores are summed in one pass. The variance matrix is checked symmetric with no negative variance after every fit (section 11.1), a failure being Z9001.

**Weights.** `weights:` with `weight_type:` (frequency, analytic, sampling; sampling by default, as the catalogue says) enters the design: a row with `NA` weight is dropped with the others, a zero weight leaves its row out of the estimate and the count with a note, a negative weight is Z0224 listing the rows (a code the specification did not give; logged), and a frequency weight must be a whole number (Z0401). The design carries each row scaled by the square root of its weight, so the fit is weighted least squares on the same kernels and the fitted leverage is the weighted one; the residuals and fitted values the fit value keeps are unweighted. Under frequency weights N is the sum of the weights, the degrees of freedom their sum less k, and in the sandwich every row stands for its weight's worth of observations, each of leverage hᵢ/wᵢ, whose score products sum to the row's divided by its weight; analytic weights are scaled to sum to the rows (Stata's `aweight`), which makes the classical variance R's `lm(weights =)`; sampling weights are probability weights, with which `se:` defaults to `robust` and `classical` is Z0410, as section 6 says; `hc2` or `hc3` together with `cluster:` is Z0410 too. R² with weights is about the weighted mean, as R computes it. The summary's N line says when N is the sum of the weights and how many rows a zero weight left out, and a line `weights: hours (sampling)` names the weighting (an addition to question 3 (a)'s layout, which did not foresee weights).

**Clusters.** The cluster variable's values group the rows used by identity, whatever its type; one cluster is Z0802, since G − 1 is zero; clusters of one observation are counted in a note (section 6: "one-observation clusters are reported"); fewer than 30 clusters is W1002 (section 11.1).

**The warnings' rules.** W1003: the weights are extreme when Kish's effective sample size (Σw)²/Σw² is below a quarter of the rows used, which is a design effect above 4, the point at which the weights have cost three quarters of the sample. W1006: an observation drives a coefficient when its removal would move some estimate by more than one standard error, a DFBETAS beyond 1 (Belsley, Kuh and Welsch's 2/√n flags a share of any large sample; one standard error is a change a reader would notice), computed from the leave-one-out formulas with the row's residual and leverage in one pass over the design; the first five rows are named. Both thresholds are constants of `regress::reg`.

**The kept design.** A fitted design and its fit are kept for the run under the frame's table, the formula as written and the weighting, so that another `se:` or `cluster:` on the same frame and formula reuses the factorisation (section 8.3, point 10, "Reused model matrices"); the table itself is held so that its address cannot be reused by another frame. One entry, the most recent; a property test demands the same bits from the reused design as from a fresh one.
