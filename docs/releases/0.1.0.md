# Release 0.1.0: First engine

Planned 18 October 2026. Scope: the 0.1.0 row of section 14 of the Engine and Project Specification. Unlocks: descriptive statistics on a CSV.

Ten functions: `frame`, `import`, `n_rows`, `n_cols`, `variables`, `describe`, `mean`, `sd`, `summary`, `print`. Each ships with the complete help page of section 9.1.

How to read this file. Each step is small enough to finish and commit in one session. The tag says which kind of session it is: **[engine]** for a hard engine piece, **[function]** for a catalogued function on machinery that already exists. A step is ticked only when it is green and committed. The specification freeze (open decision #40) is in force: corrections are logged in `docs/spec_changes.md`, and any other design question becomes a new open decision.

## Questions only the owner can answer

These concern the printed form of the ten functions (Language Reference, sections 3.8 and 10.2), which the specification leaves open. None blocks the first steps; the first one needed is step 18.

1. **`describe`, the "example" column.** Section 10.2 shows one example value per variable. Which value? Recommendation: the first non-missing value in the file, so the same file always shows the same value.
2. **Printing a frame (header, then the first ten rows).** The specification does not say what happens when the columns are wider than the line. Options: wrap the columns into blocks, as R does (recommended), or cut the line and mark it with an ellipsis.
3. **`summary`, the `stats:` argument.** The table has six statistics: N, missing, mean, SD, min, max. Recommendation: `stats:` takes a list of those six names as words (`n`, `missing`, `mean`, `sd`, `min`, `max`), in the order the owner writes them, and nothing else in 0.1.0 (no median or quantiles).

## Rulings taken from the specification (engineering; each is recorded in `docs/decisions.md` in the step that needs it)

- Help examples cannot use `import("zeff:wages.csv")`: the `zeff:` data root arrives in 0.2.0. In 0.1.0 the examples build their data with `frame(...)` or read a small file from a fixture project that the example runner supplies. They move to `zeff:` files in 0.2.0.
- `zeff check` in 0.1.0 checks function names, argument names and counts, and types. Variable names are checked when the statement runs (the schema pass behind `zeff check` is 0.6.0), with the same diagnostic.
- `import` registers only the options that work in 0.1.0 (CSV: `delim`, `header`, `skip`, `na_values`, `types`, `names`). The catalogue signature is the 1.0 signature; the options of later formats and the rest of the CSV options (`quote`, `decimal`, `thousands`, `encoding`) join the registered signature in the release that implements them (Language Reference, section 6.1: "options complete in 0.2.0").
- `parquet` is pinned with `arrow` but is not linked into the engine until 0.11.0 (smaller browser bundle, risk R4).
- Run records, `.zeff/schemas/` and the result cache are not in 0.1.0 (section 14 gives them to 0.6.0 and 0.11.0), so `zeff run` prints no `run recorded:` line yet.
- Fuzzing and message snapshots start in 0.2.0 (Language Reference, section 11.1); snapshots of the 0.1.0 messages are kept from the first diagnostic anyway.
- Constructs the grammar has but 0.1.0 does not run (`fn`, `for`, `use`, `case`, `if`, `model`, `dag`) are parsed into the tree where cheap and refused with a diagnostic. That diagnostic needs a code the specification does not list: proposed as Z0304 in open decision #41, raised in step 6 together with two other missing codes (not an owner question; deadline 0.1.0).

A final job compares the hashes and fails on any difference. - [x] **4. [engine] Bundle size and cold start tracked on every build.** Sections: risks R2 and R4; Testing 1 (bundle and start-up). Done when: numbers appear on every CI run and the failure threshold is shown to work.
